Portfolio fork of **Bello SGE**, a real internal ERP I built for
[**Bello Aramados**](https://www.belloaramados.com), a company that
manufactures wire, wire mesh, fencing, and similar products. The original
app runs in production at the company; this fork swaps the real backend and
authentication for mock versions, while keeping the entire UI, the
config-driven table/form system, and the business logic intact.

## About the system

**SGE** (Sistema de Gestão Empresarial / Enterprise Management System) is
the internal ERP for [Bello Aramados](https://www.belloaramados.com). It
covers the company's operational workflow end to end:

- **PCP (Production Planning & Control)**: production scheduling queues,
  machine assignment, work logging, operator registration, quality
  inspections;
- **Sales**: customer orders, shipments, customer registration;
- **Fiscal**: invoicing queue, invoices (notas fiscais), carriers, price
  list;
- **Purchasing**: purchase orders, suppliers, post-approval workflow;
- **Finance**: payment queue, revenues, cash flow forecasting, banks, cost
  centers;
- **Admin**: users, department-based permissions (RBAC), audit log.

## What this demo has and doesn't have

**✅ Has:**

- The entire **UI** and **navigation** of the real system, with no
  simplification;
- **Functional granular RBAC:** each _persona_ sees and edits only what
  their role would allow in the real system;
- **Mock data**, but internally consistent: an order generated by the
  `seed` already has production orders, shipment, and invoicing genuinely
  derived from it, not standalone records;
- The real **business logic**: generating production orders from an order,
  invoicing calculations, payment queue, approval flow for Purchasing order
  changes;
- An **onboarding** tour per _persona_ and a way to _reset data_ at any
  time.
  - \*_demo-exclusive feature_.

**❌ Doesn't have:**

- A **real backend**: no _SharePoint_, no _Microsoft Graph_, no database;
- **Real authentication**: no _Azure AD/MSAL_, login is a _persona_
  selector;
- **Persistence across sessions**: data lives in `sessionStorage` and
  resets when the tab is closed (or via the reset button);
- Real **email** sending or **file upload** (uploads become a local
  in-browser _Blob_);
- **Real-time collaboration** between different users/tabs.

## Stack

- **[Next.js 16](https://nextjs.org/)** (App Router, Turbopack) + **React 19** + TypeScript
- **Tailwind CSS v4** + **[shadcn/ui](https://ui.shadcn.com/)** (Radix primitives) + Fluent UI / Phosphor icons
- **[TanStack Table](https://tanstack.com/table)** (virtualized with `@tanstack/react-virtual`), **TanStack Query**, and **TanStack Form**
- **[Zod](https://zod.dev/)** for schema validation and **[next-safe-action](https://next-safe-action.dev/)** for server actions
- **[nuqs](https://nuqs.dev/)** for filtering/sorting/pagination synced with the URL
- **[Zustand](https://zustand.docs.pmnd.rs/)** (in this demo, it's the `store` that replaces the backend, as described below)
- **Vitest** + **Testing Library** for tests, **ESLint** (flat config) + **Prettier** + **Husky/lint-staged** for everything else
- In the real app (not in this demo): **Microsoft Graph API** over **SharePoint Lists** as the backend, **Azure AD / MSAL** for authentication

## Architecture: real app decisions vs. demo adaptation

The real app doesn't use a traditional database: the backend is
**SharePoint Lists**, accessed via the **Microsoft Graph API**, with
**Azure AD/MSAL** handling authentication and a granular RBAC (per user x
department) controlling what each person can see and edit. This choice
(running the entire ERP on top of SharePoint lists the company already had
licensed, instead of standing up a database and a custom API) was made with
[Bello Aramados](https://www.belloaramados.com)'s context in mind, since
the company already had its entire data architecture stored in Microsoft
solutions;

The design of the granular RBAC (Role-Based Access Control) was also built
to respect the configuration I set up within Bello's Tenant and the many
componentized security groups in Entra ID, which was then ported over into
the SGE's logic.

I also decided to generate most of the CRUD screens from `config` instead
of hand-coding each table/form.

Claude Code came in for implementing these decisions (code, refactors,
debugging hydration/race-condition bugs, etc.).

In this demo, each of these pieces was swapped for a client-side
equivalent, **keeping the same public API**, so there was no need to touch
the business logic or the UI:

| Piece                  | In the real app                                                                                                      | In this demo                                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Authentication         | Azure AD / MSAL (`app/auth/msalInstance.ts`, `MsalProvider`)                                                         | Persona selection in `lib/demo/personas.ts`, session in `lib/demo/session.ts` (Zustand + `sessionStorage`)                                 |
| Backend / data         | SharePoint Lists via Microsoft Graph (`hooks/listsService.ts` calling `/$batch`, etc.)                               | `lib/demo/store.ts`: Zustand store with the same API (`getItems`/`createItem`/`updateItem`/`deleteItem`), persisted in `sessionStorage`    |
| Site/list mapping      | `lib/sitesConfig.ts` with real SharePoint `siteId`/`listId` values                                                   | Same file, IDs swapped for logical keys pointing to the demo store's registry                                                              |
| Server-side API routes | `lib/api_ordens/graphAppClient.ts` (Graph app-only) + Route Handler `app/(protected)/api/comercial/pedidos/route.ts` | `lib/api_ordens/graphAppClient.ts` reimplemented on top of the store, called directly from the client (no Route Handler, no signed cookie) |
| Server actions         | `lib/actions/*.actions.ts` with `"use server"`, validating RBAC against a signed cookie (`bello_permissions`)        | The same actions, without `"use server"`: they run in the browser, validating RBAC against the active persona                              |
| Tables/forms           | `lib/formConfig.ts` + `config/*.config.ts` generating UI via `DynamicTable`/`DynamicForm`                            | **Unchanged**: it's the same config-driven system from the real app                                                                        |
| Business rules         | `lib/api_ordens/createOrder.ts`, `lib/api_faturamento/calcularFaturamento.ts`, `lib/api_financeiro/automacoes.ts`    | **Unchanged**: same logic, only the data layer behind it was swapped                                                                       |

## Running locally

This repo uses [pnpm](https://pnpm.io/):

```bash
pnpm install
pnpm dev
```

Open [http://localhost:3000](http://localhost:3000): the login screen
already shows the persona selector, no environment variables required.

Other commands:

```bash
pnpm build   # production build
pnpm start   # runs the production build
pnpm lint    # ESLint
pnpm test    # Vitest
```
